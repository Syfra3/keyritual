# Native macOS development build

Requires macOS 13+, Xcode command line tools (`xcode-select --install` if not already available), and an installed Rust toolchain with this repository's dependencies cached or available. From the repository root run `bash macos/build.sh`, then `open macos/build/Keyritual.app`. The script builds a release Rust engine for the **current host architecture** (arm64 on Apple Silicon, x86_64 on Intel), compiles SwiftUI with `swiftc`, and bundles the engine. This is an unsigned source build, not an installer or universal release. No Linux build or plugin installation is modified.

Select time (15/30/60 seconds) or words (10/25/50), choose strict/punctuation/numbers, then Start. Click the outlined input area to focus it; type and use Backspace to correct. Command-R or Restart starts a fresh run with the selected options. Restart waits for the previous child to exit on a background task before launching its replacement; repeated restarts keep only the latest selected options without blocking the UI. A running timer polls the Rust engine every 200 ms. Results, including comparison and pace when available, are shown after completion; strict failure is not recorded. If the engine exits, an error is shown and Restart can launch a new child.

After starting a session, enable optional pattern collection to allow local aggregate counts of expected letters and letter pairs from completed sessions. Targeted practice favors words matching those patterns and falls back to ordinary words until enough data exists. Clearing the pattern data leaves history and the enabled setting intact; disabling collection preserves the aggregates. The macOS controls and their live behavior have not been verified on a macOS host.

The child receives `XDG_STATE_HOME=~/Library/Application Support/Keyritual/state` and `XDG_CONFIG_HOME=~/Library/Application Support/Keyritual/config`; Rust stores `keyritual/history.json` and `keyritual/preferences.json` beneath these directories. No Linux XDG location is read or written. The app exposes one macOS `Window` scene and keeps its engine at app scope, so there is only one window/child and one in-memory history owner in this app instance, including after closing and reopening the window. Closing the window closes its input and terminates its child. This does not coordinate separate app processes launched outside the normal single-instance macOS app lifecycle.

Manual macOS acceptance procedure: build and open the app; start each mode, change limits and options, type and correct characters, wait for a timed finish or complete a words prompt, inspect live and finished scores; run strict with an incorrect key and verify failed state; restart and verify prior/best comparison persists; kill the child while running and check the visible error/restart path; rapidly restart several times and verify only one child remains and the latest options apply; close the window and check no child remains. Attempt to open another app window and verify no second window/child is created. These steps require a macOS host and are **not verified on Linux**.
